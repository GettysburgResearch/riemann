All acceptance gates raise explicit exceptions. Both the ordinary Python run and the run with the -O option produced identical PASS output and identical report bytes. There are no optimization-disabled assert statements in the diagnostic.

The diagnostic checks algebra and exponent bookkeeping. It does not prove the native second moment, a large sieve, theta automorphy, a Mellin contour shift, a zero-free region, a new global moment, or RH. No new Lean build is claimed.

## Source and deliverable integrity

From the repository root run:

    python standalone/2026-10-10-sextic-separated-cores/checks/verify_packet.py

The verifier requires a complete packet inventory with canonical paths and no symlinks. It checks every listed file size and SHA-256 hash, seventeen pinned source copies and their Git blob identifiers, each locked commit/path-to-blob relationship, and the exact target hashes stated in the review reports. Five adjacent files are preserved as snapshots; twelve source copies are retained in the inherited branch. Sparse-checkout omissions are read from the current Git tree.

The verification command does not access the network. Its full source-pin check requires the seventeen listed source objects to be available in the local Git database, as they were for this review. If an adjacent-source commit is missing from a fresh clone, fetch that exact commit from the repository before rerunning the verifier; it reports the missing locked identifier. The preserved snapshots remain readable independently of that Git-object check.

MANIFEST.json excludes its own hash to avoid a circular definition. The final remote verification compares its complete committed bytes, the parent and tree identifiers, and every changed blob against the local staged deliverable. Publication status is reported only after that read-back; creating a local file or commit is not treated as a push.
