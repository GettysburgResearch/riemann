# Isolated return131 build plan

`build_return131.py --prepare` is source-only: it validates PR94 contract commit `e5a82f72d8ff39a3cc1ad044e6acd727e77a3fc4`, snapshots sources into `/workspace/scratch/chain131-return-build/src`, overlays the isolated 1/250 floor and return131 sources, checks the six passed gate source/olean hashes and their three recorded direct dependencies, and pins SHA-256 for every reusable baseline olean, checks all gate dependency paths avoid changed local modules, and writes an exact source/dependency/build plan. It does not run Lean. A successful prepare in this workspace produced 4,922 local closure modules: six reused gate oleans, 4,738 unchanged baseline oleans and 178 modules requiring fresh elaboration. The staged import graph is parsed from sources; untouched source edges come from the pinned PR94 contract. A separate static reviewer found the same 62 staged modules and 122 additional reverse dependents.

Do not execute while NanoDa or another Lean/kernel process is active. With adequate resources, the explicit later command is:

```sh
python research/exploratory/2026-10-29-chain-extension/lean-draft/build_return131.py --execute --max-wall 3600
```

The driver refuses while a `lean`, `leanchecker`, or `nanoda_bin` process is visible, or the memory cgroup has less than 10 GiB available headroom. It copies the baseline and gate oleans used by the closure into a **filtered** isolated cache and puts only the isolated output, filtered cache and pinned external package directories on `LEAN_PATH`: qproject's complete olean directory is never exposed. In particular no old olean for a changed module or any of its reverse dependents is visible. It verifies source and compiler hashes, the three recorded direct gate dependency hashes, the gate artifact hashes, and all 44,577 external artifacts in qproject's pinned inventory; it rejects unpinned package olean, IR and shared-library artifacts and rechecks package bytes after the run. It records byte digests of the installed toolchain libraries and Lean’s resolved dynamic libraries before the first Lean process, checks them on every resume and at the end of the run. These checks prevent unnoticed drift during the build, but they do not establish the historical provenance of pre-existing baseline or transitive gate oleans.

Modules run in topological order, one process and one Lean worker at a time. The default per-module time limit is 360 seconds; generated admissions and edge/cover certificates receive 900 seconds. Each process has a hard 12 GiB address-space limit, plus a sampled 8 GiB resident-memory stop at 0.2-second intervals. The resident limit is not a hard allocation limit and may be exceeded between samples. The overall default execution budget is 3,600 seconds, including the current module, and it can be resumed. There is no parallel scheduling. A failure removes that module's output, records the error, and stops; after a source fix generate a new frozen plan, rather than edit the frozen snapshot. An interrupted run can resume only with the same plan, source hashes, filtered-cache hashes and each completed module's recorded direct dependency hashes. Disk availability must exceed the still-uncopied cache size by 1 GiB.

The final module explicitly invokes the four source suppliers and prints the theorem's axioms. The driver rejects missing reports and axioms other than `propext`, `Classical.choice`, and `Quot.sound`, and scans the staged sources for proof escapes after removing comments and strings. A pass would establish only isolated elaboration against these cached dependencies. For a full artifact claim, independently replay the complete 4,922-module dependency closure with a fresh trusted checker and the exact package/toolchain snapshot; do not rely on source hashing to validate olean provenance. Check the actual theorem type and source/physical/count wiring, retained floor patch and 33 admissions. No tracker submission or admission is implied.

The gate manifest records the three direct dependencies, not hashes of every transitive gate dependency at gate-build time. Therefore the six-gate reuse is a provisional acceleration: a full independent replay of the exact final environment is still required. In particular, if any transitive dependency fails provenance or checker validation, rebuild all six gates in the verified environment and rebuild every affected consumer. The current driver and final endpoint have not been executed; the NanoDa guard has been exercised and refused the live process as intended.
